# Test Data Factory - Product Requirements Document

Create a product requirements document (PRD) in markdown for Test Data Factory (TDF), a unified tool for generating synthetic test data for relational databases

Save the document as docs/PRD.md

## What problem are we trying to solve?

Engineering teams frequently struggle to obtain suitable test data.

Common approaches include:

1. Manually creating small sets of test records.
2. Copying or masking production data.
3. Generating random values using libraries such as Faker.
4. Using statistical models to create synthetic datasets.
5. Maintaining bespoke scripts for individual testing scenarios.

These approaches have limitations.

Random generators may produce structurally valid but semantically inconsistent records.

Production-derived datasets may introduce privacy, security and operational risks.

Statistical generators may reproduce distributions without preserving important business rules.

Manually maintained test fixtures can become difficult to maintain as application schemas evolve.

Performance testing often requires specially constructed data distributions that do not naturally occur in production samples.

Existing solutions also frequently separate data profiling, generation, validation and repair into disconnected workflows.

TDF aims to provide a unified approach.

## Objectives

Generate datasets according to explicit testing objectives, rather than relying on a single universal generation strategy.

Define measurable expectations that generated datasets must satisfy or intentionally violate.

Use database schemas, relational dependencies, profiling observations and generation policies to construct execution plans.

Support deterministic data generation where the chosen algorithm permits it.

Generate data across related tables while preserving declared structural constraints, except where violations are explicitly requested.

Support large-scale generation with bounded resource consumption and measurable performance.

Allow new generators, profiling metrics, expectations, validators and repair strategies to be introduced without redesigning the core system.

Explain which generation strategies were selected, which expectations were evaluated and why generated datasets passed or failed validation.

Provide a foundation for learning from generation failures and improving subsequent generation plans.

## Concepts

### Data Profile

A Data Profile represents observed characteristics of an existing dataset.

Profiles provide evidence about source-data structure, quality and statistical behaviour.

Profiling results are observations, not automatically approved requirements.

### Expectation

An Expectation defines an assertion about a dataset.

Expectations may describe:

- Structural requirements.
- Completeness.
- Uniqueness.
- Valid ranges and enumerations.
- Referential integrity.
- Statistical distributions.
- Business rules.
- Expected negative-test violations.

Expectations may be inferred, imported or explicitly declared.

### Generation Contract

A Generation Contract defines the requirements governing synthetic-data generation for a table or other supported generation scope.

Contracts establish the intended testing outcomes and applicable policies.

### Generation Policy

A Generation Policy defines how a contract is fulfilled for a particular generation intent.

Policies coordinate column groups, generator selection and applicable expectations.

### Column Group

A Column Group identifies columns that must be generated together.

Column grouping supports correlated attributes, consistent business concepts and coordinated generation.

### Generator

A Generator is an executable capability responsible for producing synthetic values.

Generators are reusable and should remain independent of particular datasets where practical.

### Generation Plan

A Generation Plan is the resolved set of execution instructions derived from contracts, policies, column groups, metadata and available profiling observations.

It identifies the selected generators, dependencies, parameters and validation requirements.

### Generation Run

A Generation Run represents one execution of a generation plan, including its configuration, seed, outputs, validation results and execution metadata.


## Functional Requirements

### Database Metadata Management

- The system should support registration of a database and its associated tables.
- The system should represent tables and their associated columns.
- The system should capture column names, logical data types, nullability and other relevant structural characteristics.
- The system should represent relationships between tables, including:
    - Relationship direction.
    - Cardinality.
    - Parent and child keys.
    - Composite keys.
    - Optionality where known.
- The system should detect invalid or unresolved metadata references.
- The system should support querying table dependencies to assist generation planning and ordering.

### Data Profiling

- The system should profile supported source datasets and produce a Data Profile.
- The initial profiling capability should support applicable metrics including:
    - Row count.
    - Null count.
    - Non-null count.
    - Distinct non-null count.
    - Minimum value.
    - Maximum value.
    - Mean.
    - Standard deviation.
    - Value set for bounded-cardinality columns.
    - Value frequencies.
- Each profiling observation should identify the metric used, measured value, applicable column and profile segment.
- The system should support profiling an entire table and, in a later increment, selected subsets of records.
- Profiles should preserve enough metadata to identify their source, profiling configuration and execution time.
- The system should support multiple profiles for the same table without silently overwriting previous observations.
- Large categorical distributions, histograms and other complex profiling outputs may be stored in external artefacts referenced by the metadata graph.

### Expectation Management

The system should maintain a catalogue of supported expectation types.

Initial expectation families should include:

- Schema and type.
- Completeness.
- Uniqueness.
- Range and enumeration.
- Statistical.
- Volume.
- Relational integrity.


Each expectation should define its type, target scope and relevant validation parameters.

The system should distinguish inferred, explicitly declared and imported expectations.

The system should support proposed and approved expectations, with rejection or retirement where applicable.

The system should support deriving candidate expectations from profiling observations.

Inferred expectations should not automatically become authoritative business constraints.

The system should support test scenarios requiring selected expectations to be deliberately violated.

Expectation evaluation should produce a measurable result, including relevant failures and diagnostics.

### Generation Contracts and Policies

The system should support defining and retrieving generation contracts associated with tables.

The system should initially recognise:

- `FUNCTIONAL`
- `PERFORMANCE`
- `EDGE`

The design should permit additional intents, including explicit negative and statistical-fidelity testing.

A generation contract should support one or more generation policies.

Generation policies should define column groups representing coordinated units of generation.

Each column group should identify the columns under its responsibility.

Column groups should select compatible generators based on their configured policies.

The model should support generator parameters and, when required, generator priority or fallback selection.

The system should detect conflicting generator ownership of the same column within a resolved execution plan.

The system should validate a generation contract before execution, detecting missing references, unsupported generators and inconsistent rules.

### Synthetic Data Generation

The system should support seeded deterministic generators for reproducible datasets.

The initial generators should support common relational types, including integers, floating-point numbers, strings, booleans, dates and timestamps.

Generators should be able to use applicable profiling observations when determining generation parameters.

The system should support configurable null frequencies, subject to applicable constraints.

The system should support categorical generation using declared sets or observed frequency distributions.

The system should support numeric generation within configured ranges and selected distributions.

A generator should be able to produce multiple related column values together.

The system should support generating related tables while preserving required foreign-key relationships.

The system should derive a valid execution sequence from known dependencies where possible, and report unsupported cyclic dependencies.

The system should support specifying required record counts.

The system should support configurable data skew and cardinality for performance-testing scenarios.

The system should support generating deliberate boundary cases and controlled invalid records.

The initial release should support CSV output. Parquet and database writers are subsequent priorities.

Large data generation should support incremental output without requiring the complete dataset to reside in memory.

###  Validation and Repair


The system should validate generated datasets against the expectations applicable to the selected generation policy.

Validation results should distinguish:

- Satisfied expectations.
- Unexpected violations.
- Expected violations.
- Unsupported or unevaluated expectations.

Generators should not determine their own validation success.

Validation failures should identify the affected expectation, dataset scope and relevant evidence.

A future capability should classify generation failures and identify candidate repair strategies.

Repair operations should be bounded by the contract and should not silently modify approved expectations.

Repaired datasets should be revalidated, including checks for regressions introduced by repair operations.

The system should preserve records of repair attempts, outcomes and unresolved violations.

A future capability should use repeated failure patterns to propose improvements to generation strategies.

Automatically proposed strategy improvements should be tested before being promoted to approved reusable behaviour.

### CLI

All essential capabilities should be accessible through a command-line interface.

The system should provide commands equivalent to:

- tdf metadata
- tdf profile
- tdf contract
- tdf generate
- tdf validate
- tdf repair
- tdf report

### Non-Functional Requirements

*Performance*

The generation engine should support streaming or batch-based processing with bounded memory consumption.

Generation throughput should be measurable in records per second.

Peak memory utilisation and generation duration should be recorded for performance benchmarks.

The architecture should permit optimised generation components written in Rust.

A future benchmark should evaluate generation of 10 million relationally consistent records on a developer workstation.

A longer-term performance target should evaluate 100 million records under documented resource constraints.

These volume targets are engineering objectives, not established performance guarantees.

*Reliability and Reproducibility*

Identical supported configurations, seeds and execution versions should produce reproducible results.

Failures should provide actionable diagnostics.

Partial output should not be reported as a successful completed dataset.

Execution reports should identify the contract, policy, generator versions and configuration used.

*Security*

The default development environment should use containers.

Coding agents should operate within a restricted development environment.

Container permissions, filesystem mounts and network access should follow least-privilege principles.

No production credentials or confidential datasets should be committed to the repository.

Source profiling should avoid unnecessary retention of raw source values.

Statistical similarity alone should not be considered sufficient evidence of privacy protection.

*Maintainability*

The system should use clearly separated responsibilities for metadata, profiling, planning, generation, validation and reporting.

Core components should expose documented contracts or interfaces.

Generator implementations should be independently testable.

The system should support local development without paid cloud services.

### Usability

Core workflows should be executable through documented CLI commands.

Error messages should identify the failure and, where practical, a corrective action.

The repository should include runnable sample configurations and datasets.

The initial release should not require a web UI.

## Proposed Technology Direction

The following technologies are proposed architectural choices, not requirements for every future deployment.

|Component|Proposed technology|Rationale|
|--|--|--|
|Orchestration and CLI|Python|Familiar ecosystem and rapid development|
|Metadata control plane|Neo4j|Visual graph modelling, Cypher and traversal|
|Graph extensions|APOC|Supporting graph operations where justified|
|Data profiling|Python / Polars|Efficient column-oriented processing|
|Initial generators|Python|Rapid development and verification|
|Optimised generation engine|Rust|Efficient high-volume generation|
|Data interchange|Apache Arrow|Columnar interoperability|
|Output storage|CSV, Parquet, database writers|Portable test data|
|Local runtime|Docker Compose|Reproducible local services|
|Development isolation|Devcontainers|Controlled environment for tools and agents|
|Testing|Pytest and appropriate integration tools|Deterministic verification|

No particular technology should be retained solely because it was selected during prototyping.

Performance and maintainability evidence should guide later architectural decisions.

## Acceptance Criteria and Example Scenarios

Given a source schema containing Customers and Orders, with Orders referencing Customers,

When a functional generation policy produces synthetic data,

Then every generated order should reference a valid generated customer, unless an intentional violation is specified.

---

Given a supported deterministic generator, fixed contract, seed and execution version,

When generation executes twice,

Then both outputs should contain equivalent records in the documented output order.

---

Given a column profile identifying a bounded set of observed categorical values and frequencies,

When a compatible profile-driven generator executes,

Then the output should use the selected generation policy to reproduce those characteristics within specified tolerances.

---

Given a contract requiring a foreign-key violation,

When the negative generation policy executes,

Then the output should contain the required violation and report it as expected rather than an accidental validation failure.

---

Given a column group containing city, state and country attributes,

When a compatible generator executes,

Then the generated combinations should satisfy the configured geographical consistency rules.

---

Given a policy where two column groups have conflicting ownership of one column,

When the generation plan is validated,

Then execution should fail before data generation, unless a supported coordination mechanism explicitly resolves the overlap.

---

Given a relational generator requiring parent records that are unavailable,

When the execution planner evaluates the dependencies,

Then it should either establish a valid generation order or report an actionable dependency error.

---

Given two profiling runs against the same table,

When observations are queried,

Then the results should be distinguishable by their profiling run and segment.

---

Given a dataset generated successfully,

When an independent validation process evaluates its expectations,

Then unexpected violations should be reported even if generation completed without execution errors.

---

Given a large requested output volume,

When the generation engine executes,

Then output should be produced incrementally, with measured memory usage and without requiring all records to be materialised simultaneously.

## Evaluation Strategy

TDF should adopt a requirements-first, evaluation-driven engineering workflow.

Unit, integration and end-to-end tests should verify deterministic functional behaviour.

When coding agents are used, evaluations should assess:

- Requirement satisfaction.
- Correct use of approved architectural decisions.
- Respect for planning and implementation boundaries.
- Unauthorised changes.
- Test quality.
- Implementation correctness.
- Human correction and rework.
- Total model expenditure.

### Data-generation evaluations

Generated datasets should be evaluated against relevant quality dimensions:

- Structural correctness.
- Relational integrity.
- Statistical fidelity.
- Scenario coverage.
- Reproducibility.
- Throughput and resource efficiency.

### Learning evaluations

Future adaptive-generation capabilities should be evaluated using repeatable benchmark datasets.

A successful improvement must demonstrate reduced unexpected generation failures or reduced repair effort without weakening applicable contracts.

## AI-Assisted Engineering Principles

AI coding agents may be used during development, but the TDF runtime should not require an LLM to generate data.

Engineering activities should follow explicit stages:

1. Requirements and acceptance criteria.
2. Domain and architectural modelling.
3. Test-case design.
4. Implementation planning.
5. Human approval.
6. Implementation.
7. Verification and review.

Agents should not begin implementation solely because a plan exists or filesystem permissions allow modification.

Model selection should be based on task complexity, reliability and measured economics.

Where possible, deterministic tools should perform tasks such as code analysis, testing, graph traversal and validation instead of relying on repeated LLM reasoning.

Engineering evaluation should consider cost per accepted task, not merely token consumption.

## Delivery Roadmap

### Phase 1 — Foundational MVP

Goal: Demonstrate deterministic, contract-driven relational generation.

Scope:

Neo4j ontology and metadata persistence.

Steelwheels Database, table and column registration.

Steelwheels Table relationship representation.

Basic profiling metrics.

Generation contracts and policies.

Column groups.

Initial deterministic generators.

CSV output.

Basic expectation validation.

CLI.

SteelWheels sample dataset.

Automated acceptance tests.

Exit criterion: A developer can generate a reproducible, relationally consistent SteelWheels dataset using a declared contract and validate it from the CLI.

### Phase 2 — Advanced Generation

Goal: Support purpose-specific testing strategies.

Scope:

Additional functional generators.

Edge-case and negative-data strategies.

Statistical and distribution-based generation.

Larger-volume generation.

Parquet output.

More advanced profiling and expectations.

Improved generation planning.

### Phase 3 — Performance Engineering

Goal: Improve generation throughput and resource efficiency.

Scope:

Benchmark generation workloads.

Identify bottlenecks.

Introduce Rust-based generation kernels where justified.

Improve streaming and parallel generation.

Establish reproducible performance benchmarks.

### Phase 4 — Adaptive Quality

Goal: Reduce generation defects through measured improvement.

Scope:

Failure classification.

Repair planning.

Bounded automatic repair.

Repair history.

Strategy improvement recommendations.

Regression evaluation of learned improvements.

### Phase 5 — Extended Test Data Management

Goal: Expand towards a broader open-source TDM platform.

Potential scope:

Additional database connectors.

Relational subsetting.

Masking and privacy-preserving generation.

Broader dataset provisioning.

Distributed generation.

CI/CD integration.

Additional statistical synthesis methods.

## Open Architectural Decisions

The following decisions remain unresolved and require further design or experimentation.

|ID|Decision|
|--|--|
|AD-001|Should testing intent be stored on GenerationPolicy or on generator-selection relationships?|
|AD-002|Should generation policies be reusable between contracts or contract-scoped?|
|AD-003|How should generator-specific configuration be represented: properties, JSON, or additional graph structures?|
|AD-004|How should profile segments represent filtering conditions and populations?|
|AD-005|How should complex profiling observations and distributions be stored?|
|AD-006|How should composite foreign keys, cyclic dependencies and multiple relationships between tables be modelled?|
|AD-007|How should expectations identify their target scopes and applicability?|
|AD-008|How should multiple generators coordinate ownership of overlapping columns?|
|AD-009|What is the appropriate initial schema for versioning contracts, policies and profiling runs?|
|AD-010|Which generation operations justify Rust rather than Python or Polars?|
|AD-011|What is the minimum useful repair mechanism before introducing adaptive learning?|
|AD-012|What should constitute the stable interface between the Python control plane and future Rust execution components?|

These decisions must not be silently resolved by coding agents during implementation.

## Product Success Criteria

The initial product should be considered useful when an engineer can:

Register a relational dataset in duckdb

Profile its tables and columns.

Define generation policies and expectations.

Generate reproducible synthetic datasets.

Preserve declared relational dependencies.

Intentionally generate selected negative and edge cases.

Validate the generated data against the intended contract.

Diagnose failures using meaningful reports.

Automate the process through a CLI.

Reproduce the workflow locally without paid cloud services.

Longer-term success will be measured through the ability to produce high-quality datasets efficiently and reduce recurring generation failures.

The defining product outcome is not the number of synthetic rows produced. It is the ability to demonstrate that those rows are suitable for the testing objective they were created to support.

## Guiding Principles

Contracts define quality.

Profiles provide evidence, not unquestionable truth.

Policies determine generation behaviour.

Generators remain replaceable.

Validation remains independent from generation.

Intentional violations are first-class testing outcomes.

Performance is measured using useful, validated output—not raw row counts alone.

Learned improvements must not weaken approved expectations.

AI may assist development but should not be a mandatory runtime dependency.

Engineering begins with requirements and evidence, not with code.

# Test Data Factory — Docker Packaging and SteelWheels Tutorial
 
**Task:** Production Docker packaging, end-to-end tutorial and verification  
**Status:** Implementation authorised, subject to the coordination rules below.

## 1. Objective

Package Test Data Factory (TDF) as a self-contained, containerised CLI application and create a reproducible, step-by-step `TUTORIAL.md` demonstrating the complete SteelWheels workflow.

The objective is to allow an engineer unfamiliar with TDF to clone the repository, build the Docker image, execute the tutorial and generate validated synthetic test data.

**The public CLI is the product interface. No agent SKILLs, web UI or additional orchestration framework should be created.**

## 2. Coordination With Existing Development

Another coding agent is currently implementing changes to the repository.

Before proceeding:

1. Inspect the current Git status and recent commits.
2. Identify any uncommitted or in-progress changes.
3. Do not overwrite, revert, reformat or interfere with another agent's work.
4. Do not assume the current implementation is final.
5. If development is still in progress, prepare a packaging and documentation plan without modifying files.
6. Begin implementation only when the existing development work is complete and the repository is in a suitable state.

Do not independently resolve merge conflicts or modify another agent's unfinished work.

## 3. Scope

The task has three deliverables.

### Deliverable A — Production Docker Packaging

Create or refine a production-oriented Docker image for the TDF CLI.

Requirements:

- Use an appropriate slim Python base image.
- Install only the application's runtime dependencies.
- Exclude development tooling, coding agents, tests and unnecessary build artefacts.
- Run as a non-root user wherever practical.
- Configure the image entry point to execute the TDF CLI.
- Provide a Docker Compose configuration containing TDF and Neo4j Community Edition.
- Include APOC only if required by the implemented functionality.
- Configure container networking, environment variables and persistent volumes.
- Mount input datasets and output directories using documented paths.
- Do not embed credentials in the image.
- Do not require privileged containers or access to the host Docker socket.
- Preserve the existing devcontainer configuration.

The preferred command interface is:

```bash
docker compose run --rm tdf --help
```

The CLI container does not need to be a continuously running service.

Do not introduce unnecessary infrastructure.

### Deliverable B — `TUTORIAL.md`

Create a root-level `TUTORIAL.md` titled:

**Test Data Factory — SteelWheels End-to-End Tutorial**

The tutorial must use actual implemented CLI commands.

It must not describe proposed features as if they already exist.

Include the following workflow.

#### Step 1 — Prerequisites

Document required tools, supported environment, dependencies and configuration.

#### Step 2 — Build the Docker Image

Provide exact commands for building and verifying the production image.

#### Step 3 — Start Neo4j

Start the required services using Docker Compose.

Verify Neo4j readiness and explain how to access Neo4j Browser.

#### Step 4 — Inspect SteelWheels

Introduce the sample dataset and its relevant tables, columns and relationships.

Use only actual sample-data structures.

#### Step 5 — Register the Database

Demonstrate database registration and metadata discovery or initialisation.

Verify registered databases, tables, columns and supported relationships.

#### Step 6 — Profile the Data

Run profiling against selected SteelWheels tables.

Inspect supported profiling metrics, profiles, segments and observations.

Explain how these observations can inform generation.

#### Step 7 — Create a Generation Contract

Create or load a contract for a selected table.

Verify its association with the table.

#### Step 8 — Configure a Generation Policy

Demonstrate the supported generation-policy workflow.

Use a functional testing intent.

#### Step 9 — Configure Column Groups and Generators

Demonstrate the association of column groups with generators.

Explain how coordinated column generation works.

#### Step 10 — Define Expectations

Create or configure supported expectations.

Demonstrate their association with the generation policy.

Explain the distinction between profiling observations and generation requirements.

#### Step 11 — Generate Synthetic Data

Run the generation command with an explicit record count and seed, where supported.

Show the resulting output location and a small sample.

#### Step 12 — Validate the Generated Data

Run validation against applicable expectations.

Explain the result and demonstrate at least one meaningful quality check.

#### Step 13 — Inspect the Ontology

Provide read-only Cypher queries that visualise:

- Database → Table → Column.
- Table → GenerationContract → GenerationPolicy.
- GenerationPolicy → ColumnGroup → Generator.
- GenerationPolicy → Expectation.
- DataProfile → ProfileSegment → ProfileObservation → ProfileMetric.
- Table → Table relationships.

All queries must match the actual persisted ontology.

#### Step 14 — Clean Up

Explain how to stop the environment safely.

Distinguish normal shutdown from destructive volume removal.

Do not delete unrelated development data.

### Deliverable C — End-to-End Verification

Execute the tutorial using a fresh, disposable Docker Compose environment.

Verify that:

1. The production image builds.
2. The CLI starts successfully.
3. Neo4j becomes ready.
4. SteelWheels data is accessible.
5. Database metadata is registered.
6. Profiling produces inspectable observations.
7. Contracts and policies can be configured.
8. Column groups and generators can be inspected.
9. Expectations can be configured and retrieved.
10. Synthetic records are generated.
11. Output files are accessible from the host.
12. Validation produces meaningful results.
13. All documented Cypher inspection queries work.

Record the exact commands executed and their outcomes.

Do not claim verification success based on code inspection alone.

## 4. Handling Missing Functionality

If the current CLI does not support a tutorial step:

1. Identify the exact missing capability.
2. Check whether an existing supported command achieves the same outcome.
3. Determine whether a small integration correction is sufficient.
4. Do not invent CLI commands or use undocumented direct Neo4j mutations to simulate functionality.
5. Escalate substantial functional or architectural gaps before implementing them.

The objective is **packaging and demonstrating the existing product**, not completing the entire Test Data Factory roadmap.

## 5. Documentation Quality

The tutorial must be:

- Executable from a clean checkout.
- Written for an engineer unfamiliar with TDF.
- Based on real commands and actual SteelWheels data.
- Copy-and-paste friendly.
- Explicit about environment variables and filesystem paths.
- Clear about expected outputs and verification.
- Honest about unsupported features.

Update the README to link to `TUTORIAL.md`.

Avoid duplicating the entire tutorial in the README.

## 6. Out of Scope

- Create or modify agent SKILLs.
- Add a web UI.
- Replace Neo4j or DuckDB.
- Redesign the ontology.
- Introduce Rust.
- Introduce CTGAN.
- Add autonomous repair or adaptive learning.
- Build a new agent orchestration framework.
- Introduce paid cloud services.
- Refactor unrelated application code.
- Optimise performance without an identified problem.
- Modify existing coding-agent configurations.
- Commit or push without explicit authorisation.

## 9. Engineering Principles

- Use the existing CLI rather than creating another interface.
- Keep the runtime image minimal.
- Preserve the existing architecture.
- Prefer executable evidence over documentation claims.
- Avoid speculative abstractions.
- Treat Docker packaging and the tutorial as an integration test.
- Stop when encountering an architectural decision outside the approved scope.

**Success means an independent engineer can execute the SteelWheels tutorial and obtain a validated synthetic dataset without coding agents, undocumented steps or manual intervention.**
